# Family Group Web: Chat & Location — Plan

A PWA port of [`family-group`](../family-group/plan.md). Private group chat and location
sharing over MQTT, in a browser tab.

Serverless, in the same sense the Android app is: the only infrastructure is an MQTT broker
the user already trusts, plus a static host for the files. The broker sees nothing but
ciphertext. There is no API, no account, no backend of ours anywhere in the picture.

## What a browser cannot do, said first

The Android app's headline feature is that it keeps running when you close it. A web app
cannot, and no amount of stack choice changes that. Rather than bury this:

| Android                                        | Browser                                                                                             |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Foreground service holding the MQTT connection | Tab closed → connection closed. Nothing is received                                                 |
| `LocationManager` sampling in the background   | `watchPosition` only while the page is alive; iOS Safari suspends a backgrounded tab within seconds |
| Notifications while closed                     | Would need Web Push, which needs a push server we have decided not to run                           |
| SQLCipher + hardware Keystore                  | IndexedDB + a non-extractable `CryptoKey`: origin-bound, not hardware-bound                         |
| MQTT over TCP/TLS                              | MQTT over WebSocket (`wss://`) only — **the broker must expose a WS listener**                      |

So the honest scope is: **chat and live location while the app is open, and everything you
already received available offline when it is not.** That is a real product — it is a desktop
client, a tablet on the kitchen counter, a phone for someone who will not install an APK —
and it is not a background tracker. The README will say so in the first paragraph, and the
onboarding will say so before anyone relies on it.

`family-group` remains the answer for always-on. This is the companion, not the replacement.

## Decisions

| Thing          | Decision                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------- |
| Framework      | SvelteKit + TypeScript, `adapter-static` — output is plain files on a CDN, no server runtime  |
| Styling        | Tailwind, Material-3-ish tokens mirrored from the Android theme so the two look related       |
| MQTT           | MQTT.js over `wss://` — the only mature browser MQTT 5 client                                 |
| Crypto         | WebCrypto `crypto.subtle`, AES-256-GCM. Identical wire format to Android                      |
| Storage        | IndexedDB via Dexie. Field-level encryption, not whole-database — see below                   |
| Key storage    | Non-extractable `CryptoKey` objects stored directly in IndexedDB                              |
| Maps           | MapLibre GL JS on OpenFreeMap vector tiles — the same vendor, natively a web library          |
| QR             | `BarcodeDetector` where it exists, jsQR on a canvas everywhere else (Safari, Firefox)         |
| Service worker | `vite-plugin-pwa`, Workbox precache. App shell + tiles cached; **no background sync of MQTT** |
| Target         | Evergreen Chrome/Edge/Firefox/Safari, desktop and mobile. Installable                         |

### Wire compatibility is a hard requirement

An Android phone and a browser tab in the same group must understand each other exactly. So
the envelope is copied byte for byte, not reinvented:

```
magic "FG1" | epoch:u8 | senderId:16B | counter:u64 | nonce:12B | ciphertext+tag
```

Same topic scheme, same `ctl` message types, same JSON plaintext shapes, same 64 KB
attachment chunking with the same sha256 check. Phase 1 ends with test vectors generated by
the Kotlin code and verified in TypeScript, so drift is caught by CI and not by a family
member whose messages arrive as garbage.

### Threat model, and where it is weaker

Everything in the Android threat model still applies: the QR _is_ the group secret, a kick is
advisory and not cryptographic in MVP1, and a group member can impersonate another group
member because the key is shared.

Two things are genuinely worse in a browser, and both are stated in the UI:

- **At rest is weaker.** A non-extractable `CryptoKey` in IndexedDB cannot be read out by
  script — that part is real, and it is why keys are stored as `CryptoKey` and never as raw
  bytes. But it is protected by the browser's origin sandbox and the disk, not by a secure
  element. A stolen, unlocked laptop with the profile unlocked gives up the group; a stolen
  Android phone does not.
- **The origin is trusted absolutely.** Whoever serves the files can serve different files
  tomorrow, and they would run with the keys already in IndexedDB. Android's signed APK has
  no equivalent hole. Mitigation is a strict CSP with no remote scripts, SRI on what few
  assets are external, and — for anyone who cares — the ability to run it from `file://` or
  their own host, since the build is static.

## Architecture

```
                        MQTT broker (wss://)
                     ┌──────────────────────┐
                     │  encrypted payloads  │
                     └───────────┬──────────┘
                                 │  <prefix>/<groupId>/...
             ┌───────────────────┴────────────────────┐
      Browser tab                                Android phone
  ┌──────────────────────────┐              ┌───────────────────┐
  │ Svelte components        │              │  family-group     │
  │   ↕                      │              │  (same envelope)  │
  │ Svelte stores (view)     │              └───────────────────┘
  │   ↕                      │
  │ Repositories             │
  │   ↕            ↕         │
  │ crypto      outbox       │
  │   ↕            ↕         │
  │ Dexie / IndexedDB        │
  │   ↕                      │
  │ MqttConnection (in page) │
  └──────────────────────────┘
        │
        └── service worker: app shell, map tiles, offline read
```

Source layout, mirroring the Kotlin packages so the two stay legible side by side:

```
src/lib/
├── crypto/     key vault, group keys, AES-GCM seal/open, QR payload codec
├── data/
│   ├── db/     Dexie schema, versions, migrations
│   ├── blob/   encrypted attachment store
│   └── repo/   groupRepo, messageRepo, locationRepo, outboxRepo
├── mqtt/       connection, topic scheme, envelope codec, outbox pump
├── location/   watcher + publish gate, retention pruner
├── map/        MapLibre style + attribution — the only place the vendor is named
└── stores/     the view layer's reactive projections of the repos
src/routes/     onboarding, groups, chat, map, settings
```

Two notes on the shape:

- **The connection lives in the page, not the service worker.** A service worker is killed
  whenever the browser feels like it, cannot be relied on to hold a socket, and would need
  its own copy of the keys. Putting MQTT in the page is honest about the lifetime we
  actually have. The service worker does what it is good at: caching the shell so the app
  opens instantly and reads work offline.
- **One tab owns the connection.** Multiple tabs each with their own MQTT client means
  duplicate client ids and a broker disconnecting them in a loop. A `BroadcastChannel` +
  Web Locks election picks a leader tab that connects; the others read IndexedDB and send
  through it. Ugly, but the alternative flaps forever and looks like a broken network.

## Data model

The Android schema, transposed to Dexie stores. Same names, same fields, so a person
reading both files is reading one design:

```
identity   (single row) userId, displayName, avatarBlobId, createdAt
broker     id, url (wss://…), username, password, topicPrefix, clientId
group      groupId, name, topicPrefix, brokerId, keyEpoch, isAdmin, createdAt
groupKey   [groupId+epoch], key: CryptoKey        -- non-extractable, stored as an object
member     [groupId+userId], displayName, avatarBlobId, role, lastSeenAt, isRemoved
message    id, groupId, senderId, type, body, blobId, createdAt, state, counter
attachment blobId, groupId, mime, sizeBytes, sha256, chunksTotal, chunksHave, data: Blob
location   ++id, groupId, userId, lat, lon, accuracy, speed, bearing, capturedAt
outbox     ++id, groupId, topic, payload, qos, createdAt, retryCount, status, nextAttemptAt
```

`broker` collapses host/port/tls into one `url`, because in a browser it is always a WS URL
and splitting it up only invites building an invalid one. `tlsInsecure` has no equivalent —
the browser decides what certificates it trusts and will not be argued with, which is worth
saying out loud on the broker screen since a self-signed broker that worked on Android will
simply refuse to connect here until its certificate is trusted by the OS.

Indexes that matter: `message` by `[groupId+createdAt]`, `location` by
`[groupId+userId+capturedAt]`, `outbox` by `[status+nextAttemptAt]`.

## Reliability: the outbox

Unchanged in design, and for the same reason — it is the single source of truth for "has
this left this device":

```
compose → encrypt → put outbox + put message(state=PENDING)
                          ↓
                  MQTT.js publish (QoS 1)
                          ↓
                      broker PUBACK
                          ↓
        delete outbox row, message.state = SENT
```

Offline, rows accumulate; on reconnect a pump drains oldest-first with 1s→2s→…→5min
backoff and a retry ceiling after which the row is `FAILED` and offered back to the user as
a retry. Location rows supersede rather than expire (`enqueueLatest`), exactly as Android
settled on: enqueuing a position drops whatever is still queued for that topic, which needs
no threshold to tune and cannot discard something it is not replacing.

The browser adds one case Android does not have: **the tab is closing with rows queued.**
There is no reliable way to flush. `visibilitychange` gets a best-effort drain, and beyond
that the rows are simply still there on next open, which is what the outbox is for.

## Location

`navigator.geolocation.watchPosition({ enableHighAccuracy, maximumAge, timeout })`, then the
same publish gate:

```
fix arrives
   ↓  moved ≥ minDistance since last SENT fix?
   ├─ no  → store locally only if history is on, do not publish
   └─ yes → encrypt → outbox → publish (retained)
also: publish unconditionally if > 3× interval since last publish
```

The admin's `Control.LocationSettings` — sample interval, push interval, movement gate,
retention — is obeyed here as it is on Android, because a map where each device picks its
own rate is a map where "3 minutes ago" means something different for every pin. Whether
_you_ share stays yours, defaults to off, and is never published.

What differs: there is no `minDistance` to push down into the platform, so the movement gate
is computed in JS on every fix. And sampling stops when the tab is hidden. A phone that
locked its screen looks identical to one that stopped sharing — which was already true on
Android, but here it happens constantly rather than rarely, so the map's staleness fade
carries much more weight and the people strip says "last seen" in words, not just colour.

## Attachments

Same 1 MB cap after compression, checked before encryption because ciphertext never shrinks.

```
image → canvas downscale to ≤1600px, JPEG q80 (loop q down until ≤1MB)
audio → MediaRecorder, opus in webm (Android reads it; AAC is not universally recordable in browsers)
file  → reject over cap with a clear message
   ↓ AES-GCM (per-blob nonce)
   ↓ split into 64 KB chunks
   ↓ publish each to att/<blobId>, QoS 1
receiver reassembles by (blobId, index), verifies sha256, decrypts, stores the Blob
```

The one incompatibility to resolve in phase 4: Android records AAC, browsers record opus.
Both sides must accept both mime types and play what they are given, rather than either side
transcoding.

## Phases

Each phase ends with the app building, deploying and being usable. No phase leaves a dead end.

### Phase 0 — Skeleton ✅

SvelteKit + TS + Tailwind, `adapter-static`, `vite-plugin-pwa` with the manifest and icons,
dark/light theme matching the Android palette, `build.sh` for parity with the siblings, README
stating the foreground-only scope in the first paragraph. Deploys to a static host and installs
as a PWA with nothing in it.

### Phase 1 — Identity, storage, crypto ✅

Dexie schema and all stores, the key vault, AES-GCM seal/open, envelope encode/decode, blob
store, first-run user-id generation, profile screen, "delete all data".
**Gate: cross-implementation test vectors.** It landed the other way round from what this said,
because it is the better direction: `scripts/generate-vectors.ts` writes `vectors/wire-vectors.json`
from the TypeScript codecs, and `WireVectorsTest.kt` in `family-group` opens it with the Kotlin
ones. Sealed payloads have to be compared by _opening_ rather than by byte equality — GCM nonces
are random, so two correct implementations never produce the same bytes — which means one side
must generate and the other must read. Getting this wrong is not otherwise discovered until phase
4, so it is proved here.

Two things this phase changed from the design above:

- **The vault wraps rather than stores.** Group keys as non-extractable `CryptoKey` objects
  would have been simpler and would have made phase 7's encrypted backup impossible: a key
  script cannot read is a key that cannot be written into a backup file. So the _master_ key is
  the non-extractable one, living in IndexedDB as a `CryptoKey`, and group keys are ciphertext
  under it — exactly the arrangement `KeyVault` has on the phone.
- **Nothing in the vault runs inside a Dexie transaction.** An IndexedDB transaction commits as
  soon as the microtask queue drains with no request outstanding, and every step there awaits
  WebCrypto between its read and its write, which is precisely the gap that closes it. The tests
  found this as `PrematureCommitError`; the fix is one atomic operation per step and a re-read to
  settle the race, guarded by Web Locks where the browser has them.

### Phase 2 — MQTT foundation ✅

Broker screen (URL, user, pass, topic prefix) with a live "Test connection" that reports the
real failure — bad certificate, no WS listener, auth rejected — since those are the three ways
this fails and "could not connect" helps nobody. `MqttConnection` with reconnect and backoff,
the leader-tab election, the outbox and its pump, presence and last-will wired into the topic
scheme though nothing publishes them until groups exist.

### Phase 3 — Groups and invitations ✅

Create group → random groupId + group key. Invite QR rendered on screen and a camera scanner
to join, plus a paste-the-payload fallback for desktops with no camera. Member list, admin
flag, kick, delete group, `ctl` messages.
**Gate: join an existing Android group from the browser and appear in its member list.**

### Phase 4 — Chat (MVP1 complete) ✅

Message list with virtual scrolling, send text, image picker and voice notes through the chunk
pipeline, delivery states with retry, unread counts, in-page notifications while the tab is
open. Resolve the AAC/opus question. **Ship point.**

### Phase 5 — Location (MVP2) ✅

The watcher and publish gate, the sharing toggle, retained `loc`, MapLibre map with per-person
avatar markers and staleness fade, retention pruning, the admin settings page for anyone who is
an admin. **Ship point.**

### Phase 6 — History ✅

Range picker, the group's paths in stable per-person colours, playback transport with scrubber
and speed, "delete history" per person. The three lessons the Android version already paid for
are inherited rather than rediscovered: decimate to 500 points per person for drawing only,
scrub in offsets from the start of the span rather than epoch milliseconds, and re-resolve a
relative range once a minute so "last hour" does not quietly become two.

### Phase 7 — Polish ✅

Multiple brokers with a connection per broker and a pessimistic aggregate status. Encrypted
backup/export — the same `.fgbk` container, and interoperable with the Android one, which
means PBKDF2-HMAC-SHA256 at 210,000 iterations even though WebCrypto could do better, and the
header authenticated as AAD. Desktop keyboard shortcuts. Then, shared with Android: key
rotation on kick.

### Phase 8 — Calling, part one: dialling and ringing (MVP4)

Signalling only, no audio — media is phase 9. The wire format is a contract with
`../family-group`, so it is settled, vectored and tested on its own before anything is built on
it. The messages, the `call` topic, the `ttlSec`-as-a-duration rule and the `ring` reply are
specified once, in `../family-group/plan.md` under this same heading; this section is only what
differs in a browser.

What differs is most of it.

#### A browser is a first-class caller and a degraded callee

**Tab open**, which is the normal way this app is used: full parity. MQTT is live, the offer
arrives in band, the caller's real name is known immediately, an `<audio>` element rings, and
answering is instant. This is the case worth building properly.

**Tab closed**: the service worker is woken by push and can show a notification, and that is
the ceiling. It cannot ring, and it cannot answer.

- **There is no sound.** A service worker has no `Audio`, and the `sound` option on
  `showNotification` is unimplemented in every browser. What plays is the operating system's
  one notification chime, once. There is no loop and no way to make one.
- **There is no full-screen intent equivalent.** Nothing on the web takes over a locked screen.
  A notification on the lock screen is as far as it goes.
- `vibrate` is Chrome-on-Android only and ignored elsewhere; `requireInteraction` is ignored on
  iOS.
- **iOS is the floor**: Web Push only from 16.4 and only in a Home-Screen-installed PWA, and
  `serviceWorkerReady.ts` already documents how readily WebKit leaves a cold-launched worker in
  a state where push does not arrive at all.

#### The structural problem, which is worse than the missing ringtone

A browser cannot hold a connection in the background — the first rule in this document. So when
a call push lands with the tab closed there is **no MQTT client alive to receive the offer**,
and the worker deliberately touches neither Dexie nor the vault (see `swIdentity.ts`), so it
could not decrypt one anyway. Therefore:

1. The notification cannot name the caller, and unlike Android there is no upgrade-in-place
   afterwards, because there is no connection to deliver the offer to.
2. "Answer" cannot answer. It focuses or opens a tab; the page boots, Dexie unlocks, leader
   election runs, MQTT connects, and only then does the offer arrive. From a cold worker that is
   plausibly 5–15 seconds, by which point the offer has expired and the caller has given up.

So the closed-tab notification says **"Missed call"**, not "Incoming call", and offers "Open"
rather than "Answer" — resolved to a real caller name once the page opens and syncs. A tap that
leads to a dead line is worse than an honest one that leads to a callback. This is the same rule
as everywhere else here: do not imply background delivery.

This is also why `ring` is in the wire format. It is the only way a caller learns the difference
between a callee that is awake and a browser tab that was closed.

#### What landed

| | |
|---|---|
| `src/lib/mqtt/callMessages.ts` | The codec, wire-identical to Kotlin's and vectored. |
| `src/lib/mqtt/topics.ts` | `callTopic`, never retained. |
| `src/lib/call/callMachine.ts` | The state machine, pure, 17 tests mirroring `CallMachineTest.kt`. |
| `src/lib/call/calls.svelte.ts` | The plumbing: Dexie, the outbox, timers, the ringer. |
| `src/lib/call/ringer.ts` | Two synthesised tones on the phone cadence, for the tab-open case. |
| `src/lib/ui/CallOverlay.svelte` | Mounted in the root layout, because a call outlives a screen. |
| `src/service-worker.ts` | A call push shows **"Missed call"**, for all the reasons above. |
| `src/lib/push/pushSender.ts` | `notifyCall`, the `kind: 'call'` wake-up. |

Two things worth knowing:

- **The ringtone is synthesised, not fetched.** Two alternating sine tones on the cadence every
  phone has. A ringtone file would be another asset to cache, to get wrong offline, and to have
  no rights to. Autoplay can still refuse it in a tab nobody has touched; that fails silently,
  because the call is still on screen and a thrown error would help nobody.
- **`ring` earns its place here more than anywhere.** It is the only way a caller learns that the
  other end was a tab that could actually ring, rather than one that was closed — which on this
  platform is the difference between waiting and calling back.

Not done, and deliberately: **a missed-call entry in the group's history.** It needs somewhere to
put it, and messages are the only history this app keeps; a call is not a message. Revisit with
phase 9, when a call has a duration worth recording.

### Phase 9 — Calling, part two: voice (MVP4)

Opus over the MQTT broker, not WebRTC. The reasoning, the topic, the packet format, the
no-outbox rule and the threat-model consequence are specified once in `../family-group/plan.md`
under this same heading; this is only what differs in a browser.

Less than last time, as it happens. The browser is the *better* half here:

- **WebCodecs gives Opus directly.** `AudioEncoder` and `AudioDecoder` with `'opus'`, no library
  and no polyfill, in Chrome and in Safari from 16.4. Where Android has to query `MediaCodec` and
  may find no Opus encoder at all, a browser that has WebCodecs has Opus by definition.
- **Echo cancellation is one constraint.** `getUserMedia({ audio: { echoCancellation: true,
  noiseSuppression: true, autoGainControl: true } })` and the browser's own AEC does the work
  that on Android needs `MODE_IN_COMMUNICATION` and an `AcousticEchoCanceler` that some devices
  implement badly.
- **The jitter buffer is shared logic**, written twice and tested twice, same as `callMachine`.

What does not improve is the part that never does: **this still only works with the tab open.**
A call is the least background-tolerant thing in the app, so the phase 8 rule stands unchanged
and the copy stays honest — a closed tab gets "Missed call" and nothing else.

One thing to watch that Android does not have to: **the page must not hold the microphone open
between calls.** A `MediaStream` whose tracks are not stopped leaves the browser's recording
indicator lit, which is alarming and correct — the microphone really is still open. Tracks are
stopped on every path out of a call, the same discipline `Ringer.stop()` already follows.

### Phase 10 — Group calls (MVP5)

Ring the group, and everyone who answers joins a room. The design, the wire (which barely
changes), the late-joiner roster and the audio mixing are specified once in
`../family-group/plan.md` under this heading; this is what differs in a browser.

Very little, and for once the browser is not the weaker end:

- **Mixing is free.** Each speaker gets an `AudioDecoder` and a source node, and the
  `AudioContext` sums them — no manual 32-bit accumulation and clipping, because that is what an
  audio graph is. The Kotlin side has to do it by hand.
- **The per-speaker jitter buffer is the same class**, one instance per sender, exactly as there.
- **Rendering a participant list is a list.**

What does not change is the rule everything here lives under: **it only works with the tab open.**
A group call is not an exception, and a closed tab still gets "Missed call" and nothing else.

One thing to be careful of that Android is not: a browser tab that joins a call opens **one
microphone** and however many decoders there are speakers. The microphone track is stopped on
every path out, as `Ringer.stop()` already is — but so must every decoder be, or a long call
leaves a tab holding a decoder per person who ever spoke in it.

### Phase 11 — Buzz (MVP6)

A call became a buzz. The reasoning, the three states, the silent-switch decision and the mode on
the wire are specified once in `../family-group/plan.md`; this is what differs in a browser.

One thing, and it is the thing a browser has always been worst at: **making a noise when nobody
is looking at it.**

With the tab open, the synthesised ringer plays as before. With the tab closed there is no page,
no `Audio`, no `AudioContext`, and `showNotification`'s `sound` option is unimplemented
everywhere — so a single notification is a single chime, which reads as a message arriving, not
as a phone ringing.

What *can* be done is re-show the same notification. With the same `tag` and `renotify: true`
each one re-alerts, so the device chimes and vibrates again; repeat it on a timer and the result
reads as ringing. `service-worker.ts` does exactly that for a buzz — ten times, three seconds
apart — and stops the moment somebody dismisses it, because a notification the person has already
dealt with should not come back nine more times.

It is bounded at thirty seconds rather than the offer's ninety, for two reasons. A service worker
is killed when the browser decides it has run long enough, and a promise held open forever is the
fastest way to be killed mid-buzz. And thirty seconds of insisting is about as much as anyone
should be able to do to someone else's phone from a text field.

The push carries the mode so the worker can act on it before anything is decrypted: a buzz
re-alerts, a voice call it could not have answered anyway still says "Missed call".

## Explicitly not doing

- ~~**Web Push.**~~ Done after all, and the condition this bullet set is what changed: the
  project did stand up infrastructure. `fcm.larus.id` holds the subscriptions and relays, a
  browser cannot subscribe its own token to a topic so `/subscribe` does it server-side, and
  `src/service-worker.ts` shows the notification. It is still only a doorbell — see
  `src/lib/push/`.
- **Background sync of MQTT via the service worker.** Periodic Background Sync is
  Chrome-only, throttled to roughly daily, and gated on the app being "engaged". It cannot
  deliver a chat message and pretending otherwise would be worse than the honest limitation.
- **File System Access for blobs.** Chromium-only, and IndexedDB holds a 1 MB cap fine.
- **A native wrapper (Capacitor/Tauri).** If the answer is a native app, `family-group` is
  already the native app.

## Settled

- **Broker.** The user sets their own; the screen ships a prefilled `wss://test.mosquitto.org:8081`
  so a first run works before anyone stands up their own, with the same plain words about a
  public broker seeing topic names and traffic timing but never content.
- **Hosting.** Static files, any host, no build-time secrets. The repository holds no deploy
  credentials and the app works served from a local directory.
- **Location history is published to all members**, as on Android — everyone holds everyone's
  history so any device can draw the past without a server, retention is per-device, and new
  joiners are not backfilled.

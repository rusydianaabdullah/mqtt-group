# Family Group: Chat & Location — Plan

Private group chat and location sharing over MQTT.

Serverless: the only infrastructure is an MQTT broker the user already trusts (their own,
or a hosted one). The broker sees nothing but ciphertext. All data on the phone is
encrypted at rest.

## Decisions already made

| Thing | Decision |
|---|---|
| `applicationId` | `id.larus.mqttgroup` — the requested `id.larus.mqtt-group` is not a legal Java package (hyphens are illegal in package segments) |
| Project folder | `family-group/`, self-contained Gradle project like the sibling apps |
| minSdk / targetSdk | 29 (Android 10) / 36 |
| Language / UI | Kotlin, Jetpack Compose, Material 3 — matches `pdf-lite` and `adzan-time` |
| MQTT client | HiveMQ MQTT Client (MQTT 5, built-in reconnect + TLS) |
| Crypto | Shared 256-bit group key, generated by the admin, carried in the invite QR. AES-256-GCM per payload |
| Local storage | Room over SQLCipher; DB passphrase wrapped by the Android Keystore. Attachments as separate AES-GCM blobs in app-internal storage. Identity and broker config are rows in that same encrypted database rather than EncryptedSharedPreferences — one storage mechanism, one thing to wipe, no dependency on a library that has been in alpha for years |
| Maps | MapLibre GL vector tiles from OpenFreeMap — no API key, no account. Isolated in `map/MapStyle.kt`; the DB never knows about the map vendor |

### Threat model, stated plainly

The QR code *is* the group secret. Whoever holds it can read the group.

- The broker, and anyone with broker credentials, sees only ciphertext plus topic names.
- Losing the phone is survivable: the DB key lives in the Keystore, so the DB is useless off-device.
- **Kicking a member is not cryptographic in MVP1.** A kick is an admin-signed message that
  honest clients obey; a member who kept the key and can still reach the broker could keep
  reading. Real revocation needs key rotation, which needs per-member keys — that is MVP3
  (`Group roles`), and the schema below leaves room for it (`epoch` on every group key).
- Replay and forgery inside the group are bounded by a sender-id + monotonic counter and the
  GCM tag; we do not get per-sender authenticity from a shared key, so a group member can
  impersonate another group member. Acceptable for a family group; called out so it is a
  choice and not an accident.

## Architecture

```
                       MQTT broker (TLS)
                    ┌────────────────────┐
                    │  encrypted payloads │
                    └──────────┬──────────┘
                               │  <prefix>/<groupId>/...
              ┌────────────────┴────────────────┐
           Phone A                            Phone B
   ┌───────────────────────┐         ┌───────────────────────┐
   │ UI (Compose)          │         │ same                  │
   │   ↕                   │         │                       │
   │ Repositories          │         │                       │
   │   ↕            ↕      │         │                       │
   │ Crypto      Outbox    │         │                       │
   │   ↕            ↕      │         │                       │
   │ Room + SQLCipher      │         │                       │

   │   ↕                   │         │                       │
   │ MqttConnection (fg svc)│        │                       │

Module layout — one Gradle module (`:app`), packages inside it:

├── data/

├── mqtt/          MqttConnection, topic scheme, envelope codec, OutboxWorker, MqttService

├── map/           tile style + attribution — the only place the map vendor is named
└── ui/            onboarding, groups, chat, map, settings
```

### Topic scheme

```
<prefix>/<groupId>/msg          chat messages, QoS 1, retain=false
<prefix>/<groupId>/loc/<userId> latest location, QoS 0, retain=true
<prefix>/<groupId>/ctl          join / leave / kick / profile / settings, QoS 1
<prefix>/<groupId>/att/<blobId> attachment chunks, QoS 1
<prefix>/<groupId>/presence/<userId>  online flag, retain=true, LWT clears it
```

Retained + LWT on `presence` means a joining phone learns who is around with no server.
Retained on `loc/<userId>` means opening the map shows the last known position instantly
without waiting for the next interval tick.

### Wire envelope

Every payload on every topic is the same shape, so there is exactly one decrypt path:

```
magic "FG1" | epoch:u8 | senderId:16B | counter:u64 | nonce:12B | ciphertext+tag
```

`epoch` is the group-key generation — always 0 in MVP1, the hook for rotation later.
Plaintext inside is CBOR-ish compact JSON: `{t: "msg"|"loc"|"ctl"|..., ...}`.

## Data model

```
identity      (single row) userId, displayName, avatarBlobId, createdAt
broker        id, host, port, tls, tlsInsecure, username, password, topicPrefix, clientId
group         groupId, name, topicPrefix, brokerId, keyEpoch, isAdmin, createdAt
group_key     groupId, epoch, wrappedKey            -- PK (groupId, epoch)
member        groupId, userId, displayName, avatarBlobId, role, lastSeenAt, isRemoved
message       id, groupId, senderId, type, body, blobId, createdAt, state, counter
attachment    blobId, groupId, mime, sizeBytes, path, sha256, chunksTotal, chunksHave
location      id, groupId, userId, lat, lon, accuracy, speed, bearing, capturedAt
outbox        id, groupId, topic, payload, qos, createdAt, retryCount, status, nextAttemptAt
```

`location` stores exactly the six raw fields — no map-vendor types — so the provider can
change without a migration.

## Reliability: the outbox

Nothing publishes directly. Everything goes through the outbox, which is the single
source of truth for "has this left the phone".

```
compose → encrypt → INSERT outbox + INSERT message(state=PENDING)
                          ↓
              MqttConnection publishes (QoS 1)
                          ↓
                  broker PUBACK
                          ↓
       DELETE outbox row, message.state = SENT
```

Offline: rows just accumulate. On reconnect the worker drains oldest-first with exponential
backoff (1s→2s→…→5min cap) and a retry ceiling after which the row is marked `FAILED` and
surfaced in the UI as a retryable message. Location rows are special-cased: a stale queued
position is worse than none, so `loc` rows older than 2× the interval are dropped rather
than sent.

## Location engine

Set by the group's admin and published to every member, not chosen per phone — see phase 5:

```
Sampling  10s · 30s · 1m · 2m · 5m · 15m      how often each phone takes a fix
Pushing   30s · 1m · 5m · 15m · 30m · 1h      how often it tells the group (>= sampling)
Movement  always · 10 · 25 · 50 · 100 · 250 m before a push is worth making
Retention 1h · 6h · 1d · 7d · 30d · forever   how long each phone keeps what it has
```

Whether *you* share is the one location setting that stays yours, defaults to off, and is never
published — other members infer it from whether fixes arrive, which is the honest signal anyway:
a phone that is off, flat or out of signal looks identical to one that opted out.

The publish gate, which is where the battery is actually saved:

```
fix arrives
   ↓  moved ≥ minDistance since last SENT fix?
   ├─ no  → store locally only if history is on, do not publish
   └─ yes → encrypt → outbox → publish (retained)
also: publish unconditionally if > 3× interval since last publish (a heartbeat, so
      "stationary" is distinguishable from "phone died")
```

Implementation: `LocationManager` — the platform's own `FUSED_PROVIDER` on API 31+, GPS and
network together below it — with `minDistance` pushing the movement gate down into the system
where it costs nothing. No `play-services-location`; see phase 5 for why. One foreground service
with type `dataSync|location` hosts both the location engine and the MQTT connection, so there
is one persistent notification and one wakelock, not two.

Permissions are staged, because Android 11+ rejects asking for foreground and background at
once: `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` at the moment someone first switches their
own sharing on, and the background upgrade left to Settings' existing background-connection
toggle, which is already where this app asks to keep running while closed.

## Attachments

Hard cap 1 MB *after* compression, checked before encryption because ciphertext never shrinks.

```
image → downscale to ≤1600px, JPEG q80 (loop q down until ≤1MB)
audio → record straight to AAC 32kbps mono
file  → deflate if it helps; reject over cap with a clear message
   ↓ AES-GCM (per-blob nonce)
   ↓ split into 64 KB chunks
   ↓ publish each chunk to att/<blobId>, QoS 1
receiver reassembles by (blobId, index), verifies sha256, decrypts, writes blob
```

Chunking from day one even under 1 MB: brokers commonly cap a single message well below
that, and it makes resume-after-reconnect free.

## Phases

Each phase ends with the app building and being usable — no phase leaves a dead end.

### Phase 0 — Skeleton ✅
Gradle project matching the siblings (`build.sh`, wrapper, `libs.versions.toml`, deploy dir),
`applicationId id.larus.mqttgroup`, Compose scaffold, dark/light theme, app icon, README.

### Phase 1 — Identity, storage, crypto ✅
Keystore-wrapped DB key, SQLCipher-backed Room, all entities and DAOs, blob store,
first-run user-id generation, profile screen (name + avatar), "delete all data".
Unit tests for seal/open, envelope framing, blob round-trip.

### Phase 2 — MQTT foundation ✅
Broker config screen (host, port, TLS, insecure-TLS toggle, user, pass, topic prefix) with a
live "Test connection". `MqttConnection` with reconnect + backoff, foreground service,
outbox and its drain pump. Presence and the last-will are wired into the topic scheme and
the connection API, but nothing publishes them until groups exist in phase 3.

### Phase 3 — Groups and invitations ✅
Create group → random groupId + group key. Invite QR (group id, name, key, broker config,
epoch) with a "show QR" screen, and a scanner to join. Member list, admin flag, kick,
delete group. Control messages on `ctl`.

### Phase 4 — Chat (MVP1 complete) ✅
Message list, send text, an image picker (PickVisualMedia.ImageOnly — not arbitrary files, which
this line used to claim) and voice notes, both ≤1 MB through the chunk pipeline,
delivery states (pending / sent / failed + retry), unread counts, notifications.
**Ship point.**

### Phase 5 — Location (MVP2) ✅
LocationEngine, the settings page, foreground sharing, retained `loc` topic, realtime map with
per-person avatar markers, retention pruning worker, staged location permission. **Ship point.**

Three things landed differently from what this document specified, each deliberate:

- **The intervals are the admin's, not each phone's.** The modes table below (Off / Normal /
  Frequent / Custom, chosen per device) became one admin-set policy published to the group on
  `ctl` as `Control.LocationSettings`: sample interval, push interval, movement gate, retention.
  A map where each person picked their own rate is a map where "3 minutes ago" means something
  different for every pin on it, and nobody can tell which. What stayed per-device is the only
  thing that should be: whether you share at all, which starts off and which no admin can flip
  for you.
- **`LocationManager`, not `FusedLocationProviderClient`.** Fused means `play-services-location`.
  This project already refuses Google's libraries for QR scanning on the grounds that an app
  whose selling point is that nothing leaves the phone should not need them, and location is
  that argument at full strength. Since API 31 the platform exposes the same sensor fusion as
  `LocationManager.FUSED_PROVIDER`; below that it is GPS and network together. The cost is
  batched delivery (`setMaxUpdateDelayMillis`, 31+ only), which at a one-minute floor is a small
  price for shipping no Google code.
- **MapLibre vector tiles, not OSM raster.** Raster cannot rotate or tilt and steps between zoom
  levels, which reads as broken next to any other map app. MapLibre plus OpenFreeMap is vector,
  needs no API key or account, and — unlike every keyed free tier — does not make each pan an
  attributable request from a known application. See `map/MapStyle.kt`.

The stale-`loc`-row rule below is implemented by superseding rather than by a timeout: enqueuing
a position deletes whatever is still queued for that topic (`OutboxRepository.enqueueLatest`).
It needs no threshold to tune and cannot discard something it is not replacing in the same
breath.

### Phase 6 — History ✅
History is a mode, off by default: the map opens live, showing where everyone is now, and a
history button in the corner turns the past on. Range picker on the map (`HistoryRange`: last hour, today, yesterday, last 24 hours, last 7 days,
or dates picked by hand), the whole group's paths drawn at once in a stable per-person colour
keyed in the people strip, and "delete history" scoped to one person from their card on the map.
Unit tests for the date arithmetic.

Playback: a transport bar under the map replays the loaded span — play/pause, a scrubber, a
1x–8x speed, and "Now" to hand the map back to the present. While the playhead is set, the pins
show where each person *was* at that moment, the paths draw themselves up to it, and staleness
fades measure against the playhead rather than the wall clock. Playback state is deliberately not
in the view model: it is presentation over paths already loaded, and losing your place on
rotation is what a video player does too.

Three things worth knowing:

- **Paths are decimated to 500 points per person** for drawing only (`MainViewModel.decimate`).
  A week at the shortest push interval is tens of thousands of fixes each, and the map draws
  everyone at once. Pins, the detail card and the database all still use the real rows.
- **The scrubber works in offsets from the start of the span, not epoch milliseconds.** A Float
  carries 24 bits of mantissa, so an absolute timestamp rounds to the nearest ~2 minutes — on a
  "last hour" timeline, a slider with about thirty usable positions.
- **The range is re-resolved once a minute, not once when it is chosen.** A relative range fixed
  at the moment it was tapped silently grows: leave the map open for an hour on "Last hour" and
  it is showing two. A fixed range ignores the tick, since its window does not move.

### Phase 7 — MVP3 polish (in progress)
**Multiple brokers ✅.** A group names its own broker (`GroupEntity.brokerId`, which the schema
always carried). `ConnectionPool` holds one `MqttConnection` per broker, created on demand and
retired when the last group leaves it; `GroupSync` subscribes each group on its own broker's
connection and the outbox routes each row to its group's broker. Creating a group picks a broker
from the saved list — which is how one group copies another's settings — or adds a new one, and
a Brokers screen under Settings lists them with the groups on each.

Two things worth knowing:

- **The app-bar status is deliberately pessimistic.** With three brokers and one down, "connected"
  would be a lie to the groups on the broken one. `ConnectionPool.aggregate` reports the worst
  state; per-broker state is on the Brokers screen, which is where "which half of my groups is
  stuck" can actually be answered.
- **Client ids are per broker as well as per phone.** Two connections from one phone sharing an
  identifier means a broker kicking one off the moment the other connects, forever — and it looks
  exactly like a flapping network.

**Encrypted backup/export ✅.** Settings → Backup writes a `.fgbk` file wherever the system
picker is pointed, and restores from one. Contents: identity, brokers, groups with their
settings, every epoch of every group key, member lists. Not messages, location history or blobs —
those are the bulk, and unlike the keys they are replaceable. `BackupArchive` is the container
format and is unit tested; `BackupRepository` fills and applies it.

Three things worth knowing:

- **Group keys are unwrapped on the way out and re-wrapped on the way in.** They live in the
  database wrapped by `KeyVault`, whose master key is in *this* phone's hardware Keystore and
  cannot leave it — backing up the wrapped bytes would produce a file that restores to a phone
  which cannot open them. It would look like a backup right up until it was needed. The cost is
  that the plaintext group keys really are in the file, behind the passphrase and nothing else,
  which the UI states plainly.
- **The header is authenticated as AAD.** Salt and iteration count sit in the clear; without
  binding them to the tag, an attacker could rewrite the file to say one iteration and let the
  victim's own app do the cheap derivation.
- **PBKDF2-HMAC-SHA256 at 210,000 iterations**, because it is the only password KDF Android
  ships. Argon2id would be better — memory-hardness is exactly what defeats GPU cracking — but
  not without a native library in an app whose argument is that it carries no more code than it
  must.

Still to do: key rotation on kick (per-member X25519 identity keypairs, so the new epoch key is
wrapped once per remaining member and the kicked member gets nothing).

### Phase 7 — original scope
Image + audio capture in-app, richer notifications with per-group mute, multiple brokers,
group roles beyond admin/member, encrypted backup/export, and key rotation on kick.

### Phase 8 — Calling, part one: dialling and ringing (MVP4)

Signalling only. This phase makes a phone ring, be answered, be declined and time out; it
carries no audio at all. Media is phase 9, and splitting them is deliberate — the wire format
is a contract with `../family-group-pwa` and has to be settled, vectored and tested before
anything as large as WebRTC is built on top of it.

Scope: **one member dials one member.** Group ringing multiplies every failure mode below by
the size of the family and is not worth it before the two-party case is solid.

#### The topic

```
<prefix>/<groupId>/call               call signalling, QoS 1, never retained
```

Never retained, unlike `set` and `loc`: a retained ring is a phone that rings on subscribe for
a call that ended last Tuesday. Clients already subscribe `<prefix>/<groupId>/#`
(`Topics.everything`), so nothing new is subscribed — only a new suffix to route.

Separate from `ctl` rather than more `Control` cases, because `ctl` is where the durable facts
about a group live — membership, profile, settings — and these are the opposite: they expire,
they are worthless late, and they must not be replayed. Keeping them apart keeps that rule
visible in the topic rather than buried in a handler.

#### The messages

`Call`, a sealed interface beside `Control`, same JSON-with-short-keys framing, sealed in the
same envelope:

| Type | Carries | Who sends it |
|---|---|---|
| `offer` | `callId`, `to`, `mode` (`audio`), `ttlSec` | the caller, once |
| `ring` | `callId` | the callee, to say the offer landed and is ringing |
| `accept` | `callId` | the callee |
| `decline` | `callId`, `reason` (`declined` / `busy`) | the callee |
| `cancel` | `callId` | the caller, before an answer |
| `end` | `callId` | either side, once connected |

`callId` is a random 128-bit id minted by the caller; every later message names it. **No message
carries who sent it**: that is the envelope's authenticated sender, the same rule profile
announcements follow, so nobody can publish a ring on another member's behalf. A client that is
neither the sender nor the `to` decrypts the offer and ignores it — no notification, no UI.

**The timeout is a duration, not a deadline.** `ttlSec` (default 45) is counted by each side
from when it *locally* created or received the offer, never from a `createdAt` compared against
the local clock. Two phones in a family are routinely tens of seconds apart and occasionally
hours — a wall-clock deadline means either a ring that never starts or one that never stops,
and the bug only appears on somebody else's phone. The cost is that a delayed offer rings for
its full 45s late rather than being discarded on arrival; `ring` is what tells the caller which
of those happened.

`ring` exists so the caller's UI can say "ringing" rather than "calling" — the difference
between "your message reached a phone that is awake" and "we published into the void", which
with a PWA callee or a dozing phone is the single most useful thing the caller can be told.

#### The outbox, and the one rule this phase bends

The house rule is that everything outbound goes through the outbox so it survives a dead
network. A ring that survives a dead network is a phone ringing twenty minutes after the caller
gave up — the outbox's whole purpose is the wrong behaviour here.

So `OutboxEntity` gains a nullable `expiresAt`, and `OutboxPump` drops rather than publishes a
row that is past it. Call rows set it; everything else leaves it null and behaves exactly as
before. That keeps one send path rather than two, and puts "this was worthless late" in the
data instead of in a special case at the call site.

#### Waking a phone that is asleep

MQTT is the transport; FCM is only the doorbell, exactly as for chat. But the chat doorbell
cannot be reused as it stands:

The relay is `fcm-service` (`~/app/larus-compro/fcm-service`, FastAPI over firebase-admin,
deployed as `fcm.larus.id`). Two of the three things a call push needs are already there:

- **Priority is already high.** `send_notification` sets
  `AndroidConfig(priority="high", ttl=3600)` and a webpush `Urgency: high`, which is what gets a
  wakelock and network out of Doze in the first place. Nothing to change.
- **The `notification` payload is the blocker.** `send_notification` always attaches one, by
  design and documented as such. When it is present and the app is backgrounded, Android draws
  the tray notification itself and `onMessageReceived` **never runs** — so no code of ours runs
  and nothing can ring. A call push has to be data-only.
- **The TTL is wrong by three orders of magnitude.** `WEBPUSH_TTL_SECONDS = 3600` is right for a
  chat doorbell, for the reason its comment gives. For a call it means a push stuck behind a
  tunnel rings the phone an hour after the caller gave up. A call needs roughly the life of the
  offer: 45s.

**Done — the relay side has shipped**, because until a data-only push existed there was no way
to test a ring on a backgrounded phone at all. `/notify` now takes an optional `kind`,
defaulting to `message` so every existing caller is untouched; the phones in the family will run
an older build than the relay for as long as it takes everyone to update. `kind: "call"` sends
no `notification` block on either transport, sets both TTLs to `CALL_TTL_SECONDS` (45), and
stamps `data.kind` into the payload so a client routes the push instead of guessing from which
other fields happen to be present — `message` is stamped too, so the rule has no exception.

`title` and `body` are *refused* for a call rather than made optional. A caller that sets a
title is a caller that believes it will be displayed, and it will not be; a 422 is kinder than
someone debugging a notification that never shows the text they set.

One limitation to know rather than design around: a data-only message is not delivered to an
app the user has **force-stopped** from Settings. Neither is anything else, including the
current chat doorbell, so calling changes nothing here — but "I force-stopped it and now it
does not ring" is a support question with a real answer.

The push still says nothing. Title and body cross Google's servers in the clear, so they stay
generic; the caller's identity arrives only as MQTT ciphertext.

**Which means the ring starts before the caller's name is known.** Cold FCM wake → connect →
subscribe → receive → decrypt is plausibly 2–5 seconds. Ringing silently until it resolves
feels broken, so: ring immediately on the push with generic copy, then **update the same
notification in place** once the offer is decrypted and the name is known. A generic ring that
turns into a name reads as a phone waking up. Silence does not.

#### Ringing on a locked screen

- A `CallStyle` notification on an `IMPORTANCE_HIGH` channel, with a **full-screen intent** at an
  `IncomingCallActivity` (`showWhenLocked`, `turnScreenOn`).
- `USE_FULL_SCREEN_INTENT` in the manifest — **and a runtime check**. On Android 14+ this is no
  longer granted at install to general apps; only ones the system judges to be calling or alarm
  apps get it. So check `NotificationManager.canUseFullScreenIntent()` and, when it is false,
  offer a trip to `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`. The degraded path is a
  heads-up `CallStyle` notification, which still buzzes and still appears on the lock screen; it
  just does not take over. Build for the degraded path first and treat the full screen as the
  upgrade, or the feature is broken on every phone that declined a settings trip.
- **The ringtone is ours to play and ours to stop.** A channel sound plays once and does not
  loop. So `Ringtone`/`MediaPlayer` at `USAGE_NOTIFICATION_RINGTONE` plus a repeating `Vibrator`
  pattern, owned by the call's own foreground service, stopped on accept, decline, cancel and
  timeout alike — all four, because the one that is forgotten is the one that rings until the
  battery dies. Respect the ringer mode: silent means vibrate only.

#### What this phase does not do

- **No audio.** Phase 9.
- **No Telecom integration.** A self-managed `ConnectionService` with `MANAGE_OWN_CALLS` would
  give real lock-screen call UI, audio focus and sane interaction with actual phone calls, and
  it is also the clean route to full-screen-intent eligibility. It is a large amount of code and
  Play-review surface to commit to before the signalling has been used in anger; revisit it in
  phase 9, when audio focus stops being optional.
- **No caller authenticity.** A shared group key gives no per-sender proof, so any member can
  forge an offer claiming to be any member. Unchanged from every other message in this app, and
  the incoming-call UI must not state the caller's identity more confidently than the rest of
  the app does.

#### What landed

All of the above, in this order, with `fcm-service` first because nothing below it could be
tested until a data-only push existed.

| | |
|---|---|
| `mqtt/CallMessages.kt` | The codec. Five messages became six — see `end`, below. |
| `mqtt/Topics.kt` | `call(prefix, groupId)`, never retained. |
| `call/CallMachine.kt` | The state machine, pure, 17 tests in `CallMachineTest.kt`. |
| `call/CallEngine.kt` | The plumbing around it: identity, outbox, timers, ringer, notifier. |
| `call/AndroidCallNotifier.kt` | `CallStyle`, silent channel, full-screen intent as an upgrade. |
| `call/AndroidRinger.kt` | Looping ringtone and vibration, and the one `stop()` every path calls. |
| `ui/CallActivity.kt` | The call screen, over the lock screen. |
| `data/db/` | `OutboxEntity.expiresAt`, schema 6. |
| `push/PushSender.kt` | `notifyCall`, the `kind: "call"` wake-up. |

Three things came out differently from what is specified above, each deliberate:

- **`end` exists, and a connected call is a real state.** The five messages first planned here
  had no way to hang up an answered call, because the phase was scoped to stop at the answer.
  Stopping there would have meant shipping a wire format both apps had to change again in phase
  9. So `Call.End` landed now, sent by *either* side and only once connected — which is exactly
  why it is not another `Cancel`. Before an answer the caller cancels and the callee declines;
  after one there is no caller and no callee, only two people on a call.
- **`title` and `body` are refused for a call push, not made optional.** A caller that sets a
  title believes it will be displayed, and it will not be; a 422 beats debugging a notification
  that never shows the text you set.
- **The offer carries no sender.** Who is calling is the envelope's authenticated sender, the
  same rule profile announcements follow, so the body needs no `from` field and no member can
  publish a ring on another member's behalf. It still buys no authenticity *between* members —
  a shared key never will — so the UI says "Someone in this group" until the member list
  resolves a name, and treats that name as a claim.

And one thing was found rather than written: **`WireVectorsTest` had never run.** Its path to
`vectors/wire-vectors.json` was resolved against the project directory while Gradle runs unit
tests from the `app` module, so `assumeTrue` turned all seven of its tests into skips — a green
build with the cross-implementation gate switched off, for as long as the file has existed. It
now finds the vectors by walking up from wherever it is run, and passes. (`values-in/strings.xml`
was also missing `notification_connection_text`, which is the bug shape the root `CLAUDE.md`
warns about; that is fixed too.)

#### Found on the first real device test

`NotificationManager.notify` threw and took the process down the moment anyone pressed Call:

```
IllegalArgumentException: Not posted. CallStyle notifications must be for a
foreground service or user initated job or use a fullScreenIntent.
```

A `CallStyle` notification is not allowed to be posted at all unless it belongs to a foreground
service, belongs to a user-initiated job, or carries a `fullScreenIntent`. The incoming one had
an intent and was fine; the *ongoing* one — the caller's own "Calling…" — had only a content
intent, so dialling was a guaranteed crash on every phone.

The note written above this, that the notification is "built to work without" a full-screen
intent and the intent is an upgrade attached where it will be honoured, was simply wrong for
`CallStyle`, and is corrected in the class. Two different things were conflated: whether the
intent may be *set* (always, no permission needed, and required here for the post to be legal)
and whether it will be *honoured* as an actual full-screen takeover (Android 14 permission,
degrading to a heads-up banner otherwise). Building for the degraded path was right; leaving the
intent off to get there was not.

Fixed in 1.7.1, along with the reason a refused notification could crash anything: `CallEngine`
drives the notifier from a coroutine on the application scope, so the throw reached the default
uncaught handler. Posting is now wrapped and logged, and that scope has a `CoroutineExceptionHandler`.
A call that cannot ring is a bad call; a call that kills the app is a crash report.

Still worth doing properly in phase 9: a real foreground service for an active call. It is the
first of the three options the platform offers, it is what keeps a call alive independently of
`MqttService`, and audio focus will need one anyway.

#### Verified on hardware

Two Android phones, after the delivery fix in 1.9.1: **a call rings, is answered, and connects.**
The ringtone, the incoming-call notification, the call screen and hanging up all behave. This is
the ship point phase 8 was aiming at.

Still not exercised on a device, and worth knowing:

- **The FCM wake-up path.** Every test so far has been between two phones already connected to
  the broker. A callee whose app is fully backgrounded, or swiped away, relies on the data-only
  push and nothing has proven that end to end.
- **The full-screen intent**, as opposed to the heads-up notification. Which of the two appears
  depends on a permission Android 14 grants to almost nothing, and both are supposed to work.
- **A browser at either end.** Everything here compiles, and every piece that can be tested
  without a phone is tested, but no call has been placed between two real handsets. The ringer,
  the full-screen intent, the lock-screen activity and the push round trip are all unexercised.
- **Audio.** Phase 9, and until then both apps say on screen that the call is silent.

### Phase 9 — Calling, part two: voice (MVP4)

> **Removed from the Android app in 1.7 (9).** It was built, tested and never reachable: no UI
> ever sent `Mode.AUDIO`, so the capture, the Opus codec, the jitter buffer and `CallService`
> were dead weight carrying two foreground-service permissions — `FOREGROUND_SERVICE_MICROPHONE`
> and `FOREGROUND_SERVICE_MEDIA_PLAYBACK` — that Play asks an app to justify and that this one
> could not demonstrate. `Mode.AUDIO` survives as a word on the wire because the format is shared
> with the web app and the vectors pin it; `CallEngine.onMessage` drops an offer carrying it.
> The rest of this section is kept as the design record, and git history has the code.

Phase 8 made a phone ring, be answered and be hung up. This carries the voice, and it carries it
over the broker that is already there.

#### Why not WebRTC

WebRTC is the obvious answer and the wrong one for this product. It needs STUN to discover
addresses and, whenever a NAT refuses to cooperate, TURN to relay — which is a server, run by
someone, that learns who is talking to whom and when. That is the one thing this app has never
needed and has said so on every screen.

The deciding argument is not privacy, though. It is that `README.md` says where this is going:
mining sites, plantations, vessels, plants — "places where the network is your own, the outside
internet is unreliable or deliberately absent". On a network with no route out, STUN cannot
resolve and TURN cannot be reached, so a WebRTC call simply does not connect. A broker on the
LAN keeps working, because it is the only thing that has to be reachable and it already is.

The cost is honest and it is latency: a broker round trip instead of a direct path, so roughly
300–800ms mouth to ear rather than the 150ms a phone call manages. That is a call on a bad line.
It is not a phone call, and the UI should not pretend otherwise.

Secondary, and not nothing: it keeps ~15 MB per ABI of Google's libwebrtc out of an app that has
already turned down ML Kit and play-services-location for the same reason.

#### The topic

```
<prefix>/<groupId>/aud/<userId>       voice, QoS 0, never retained
```

**QoS 0, and that is the point.** QoS 1 would have the broker redeliver a packet that was late —
and a late audio packet is not a packet that was missed, it is one whose moment has passed. The
jitter buffer has already played silence over it. Redelivering it costs radio and delivers noise.

Per-sender subtopic, like `loc`, so two people talking at once are two streams rather than one
interleaved mess — and so the group case, when it comes, needs no new format.

#### Audio does not go through the outbox

This is the **only** exception in the app, and it is a deliberate one.

The outbox exists so a message written in a lift arrives an hour later. Applied to voice that is
not a feature, it is a guarantee to deliver something worthless: a frame that survives a dead
network is noise from a conversation that ended. Phase 8 already bent this with `expiresAt`,
which is the right tool for a ring — a handful of messages, each worth a retry for a few seconds.
Voice is the other extreme.

The mechanical reason is as strong as the design one. `OutboxRepository.enqueue` is a row insert,
and `GroupRepository.publish` calls `nextCounter`, which is a second database write. At ~25
packets a second that is fifty writes a second of pure overhead, on the phone, during a call.

So `AudioStream` seals and publishes straight through the group's `MqttConnection`. It is the one
place in this app allowed to, it is a handful of lines, and it is commented as the exception it
is. Everything else — every control message, including every call-signalling message from phase
8 — still goes through the outbox.

Two consequences to get right:

- **The envelope counter is held in memory for the life of a call**, seeded once from the
  database when the call connects, incremented per packet, and never written back. Nothing reads
  it: `/aud` is exempt from the replay check exactly as `/loc` and `/att` already are, because an
  out-of-order audio packet is ordinary and dropping the stream over it would be absurd.
- **Nonce reuse is not a risk introduced by that.** `Aead.seal` draws a fresh random 96-bit
  nonce per payload and never derives one from the counter, so a counter that restarts is
  harmless. Worth stating because the opposite design — nonce from counter — is common, and
  would have made this a key-destroying bug rather than a cosmetic one.

#### Packetisation, and why not one frame per publish

Opus at 20ms mono. But an envelope costs 28 bytes of header, 12 of nonce and 16 of tag — 56 bytes
— and MQTT adds its own topic and fixed header on top. One 20ms frame per publish is 50 publishes
a second and more overhead than payload.

So three frames to a packet, 60ms, ~17 publishes a second. At 24 kbps that is about 3 KB/s of
Opus against roughly 1 KB/s of overhead, which is a ratio worth having and a packet loss that
still only costs 60ms of speech. The payload is a tiny header — stream id, sequence, frame count
— then each frame length-prefixed, so the format does not care how many are packed.

#### The jitter buffer

The one part of this that is pure logic, so it is the part with tests: packets arrive out of
order, late, or not at all, and something has to decide what to hand the decoder every 20ms.
Sequence numbers in, frames or "conceal this one" out, no clock of its own and no audio API in
sight — the same split phase 8 used for `CallMachine`, and for the same reason. `AudioJitterTest`
on both sides.

#### Codec, and the one thing that might not exist

Opus on both ends, because it is the only codec a browser and an Android phone both have without
shipping a native library.

- **Browser**: `AudioEncoder`/`AudioDecoder` from WebCodecs. Chrome, and Safari from 16.4.
- **Android**: `MediaCodec` with `audio/opus`. The *decoder* has been there for years. The
  **encoder** arrived in Android 10 and is not guaranteed to be present on every device even so,
  because `MediaCodec` availability is an OEM matter. So it is queried through `MediaCodecList` at
  call setup rather than assumed, and a phone without one cannot place or answer a voice call —
  it says so, and phase 8's signalling still works, so the call rings and connects silently rather
  than failing mysteriously. This is the single largest unknown in this phase and is checked
  first, on a real device, before anything else here is built on it.

#### The foreground service phase 8 should have had

An active call becomes a real foreground service. Three reasons, in order:

1. It is the first of the three ways the platform permits a `CallStyle` notification to be posted
   at all — the rule that crashed the first dial and is currently satisfied by a full-screen
   intent instead.
2. A call has to outlive the activity, and right now it survives only because `MqttService`
   happens to be holding the process up.
3. Recording the microphone from the background needs one, and needs `FOREGROUND_SERVICE_MICROPHONE`
   with type `microphone` from Android 14.

#### What this changes in the threat model, and it is not nothing

**The broker carries the audio.** Still ciphertext, still openable by nobody but the group — but
the traffic pattern stops being subtle. Chat is a few hundred bytes now and then; a call is 3 KB/s
of steady packets between two named topics for exactly as long as the conversation lasts. Anyone
who can see the broker learns that two specific members spoke, when, and for how long, without
decrypting a byte.

That has always been true of the topic structure and is why the prefix is the user's to choose.
Voice makes it loud. Two things follow, and both belong in the UI rather than in this document
only:

- **A public broker is a bad place to hold a call.** `test.mosquitto.org` is a prefilled
  convenience for a first run, and it is somebody else's bandwidth and somebody else's logs.
- **Self-hosting stops being the private option and becomes the sensible one.** Which is also the
  configuration the enterprise case above already assumes.

#### What landed

| | |
|---|---|
| `mqtt/AudioMessages.kt` | `AudioPacket` — the one binary codec here, vectored against the PWA. |
| `mqtt/Topics.kt` | `audio(prefix, groupId, userId)`, QoS 0, never retained. |
| `call/JitterBuffer.kt` | Pure, 10 tests. Lost packet versus underrun is the whole job. |
| `call/AudioCodecs.kt` | Is there an Opus encoder on this device? Asked, not assumed. |
| `call/OpusCodec.kt` | `MediaCodec` either way, with the `OpusHead` the decoder insists on. |
| `call/VoiceStream.kt` | Capture, encode, publish; jitter, decode, play. Two threads, one beat. |
| `call/CallService.kt` | The foreground service an answered call should always have had. |
| `mqtt/MqttConnection.kt` | `publishNow` — the one publish that skips the outbox. |

Five things came out differently from the sketch above, each deliberate:

- **The `OpusHead` header is built, not transmitted.** Android's Opus decoder will not configure
  without codec-specific data — an identification header, a codec delay and a seek preroll, the
  three things a container normally carries. Both ends are fixed at 48 kHz mono, so each builds
  the header the other's encoder would have produced. Putting it on the wire would be nineteen
  bytes of every packet restating what both ends already know. The browser needs none of it,
  which is one more reason the parameters stay fixed rather than negotiated.
- **Playout is paced by the hardware, not by a timer.** `AudioTrack.write` blocks until the
  device will take more, so the 20ms beat comes from the speaker rather than from a clock this
  thread would have to correct against drift.
- **Muting encodes silence rather than stopping the encoder.** Stopping it leaves a gap the far
  end reads as an underrun and holds for, so every unmute would resume a beat late. The
  microphone genuinely goes unread either way, which is the part that matters.
- **`VOICE_COMMUNICATION` on both the capture and the playback side**, plus
  `MODE_IN_COMMUNICATION`, `AcousticEchoCanceler` and `NoiseSuppressor`. The audio source is what
  asks for the platform's hardware echo path; the effects are the software belt to its braces.
- **A call whose microphone permission was refused still runs.** Being able to hear someone while
  they cannot hear you is a degraded call, and a degraded call beats a dead one — the screen says
  which half is missing, and granting mid-call restarts capture rather than requiring a callback.

#### Found on the first two-phone test: nothing rang, ever

No ringtone, no vibration, no notification — and the caller sat on "Calling…" until it timed out.

`GroupSync` kept its own private set of topic kinds, separate from the one `Topics` uses to
build them. `Topics` gained `call` in phase 8 and `aud` in phase 9; that private set never did.
So `kindOf` returned null for every call topic and `handle()` dropped the message at its first
line — before decryption, before the engine, before anything. **Every call message between two
Android phones had been silently discarded since phase 8 shipped**: offer, ring, accept, hang-up
and audio alike. Nothing logged, nothing threw, nothing failed. The PWA was unaffected, because
there the list lives in `topics.ts` beside the builders and was updated with them.

The fix is the obvious one and the interesting part is the test. `Topics` now owns the kinds as
named constants, builds every topic from them, and exposes `kindOf`/`groupIdOf`; `GroupSync`
delegates. But one list can drift again the moment someone adds a topic, so `TopicsTest` walks
*every builder* and asserts the receive side recognises what it produced, rather than restating
the list — a new topic without its kind now fails in CI instead of in somebody's living room.
Verified by putting the bug back: the test fails with `no kind for house/family/g-1/call`. The
PWA has the same test, for the same reason.

Worth saying plainly: this was invisible to every test that existed. The codecs were verified
against shared vectors, the state machine had seventeen tests, the jitter buffer had ten — and
none of them touched the one line that decides whether a message is delivered to any of it. The
seam between two correct components is where this class of bug lives.

#### Verified on hardware, and then made usable

**People can hear each other.** Two Android phones over a broker, first confirmation that the
whole path carries real sound: capture, Opus encode, publish, jitter buffer, decode, play.

The first report of it was also the first complaint about it — **the delay was very long** — and
the arithmetic said most of it was ours rather than the network's:

| | before | after |
|---|---|---|
| Frames held back to fill a packet | 3 × 20ms = 60ms | 2 × 20ms = **40ms** |
| Jitter cushion before playout starts | 3 packets = 180ms | 2 packets = **80ms** |
| Output buffer | 4 frames = 80ms | 2 frames = **40ms**, low-latency mode |
| **Added by this app** | **320ms** | **160ms** |

Both numbers were first guesses made with no call to measure, and both were cautious in the
wrong direction. The jitter cushion was the worst of it: 180ms spent insuring against reordering,
on a path whose jitter is small compared to its latency. Bandwidth went from 24 kbps to about 36,
which nobody will notice, and which is the right side of that trade.

Neither figure is a wire change. The packet carries a frame count, so a phone packing three still
talks to one packing two, and the cushion is a receiver's own business.

**What tuning cannot fix is the path to the broker**, so the call screen now shows it: the offer
is published, the callee's `ring` comes back, and the difference is a genuine round trip timed on
one phone's monotonic clock — no clock agreement needed, which is the same trap `ttlSec` avoids.
A broker on another continent costs a few hundred milliseconds that no amount of work here will
recover, and the only answer is a broker that is closer. The number says which problem you have.

### Phase 10 — Group calls (MVP5)

Calling the group rings every member, and each one who answers joins a room that already holds
whoever got there first. People come and go while it runs; it ends when the last person leaves.

Video is deliberately not in this phase — see "Why video waits" at the end.

#### Why this suits the broker, where video does not

A broker is a fan-out. Each speaker publishes **once**, to their own `aud/<userId>` topic, and
every other member receives it because they are already subscribed to `<prefix>/<groupId>/#`. So
a five-person call costs each phone one upstream at 24 kbps and four downstream at 24 kbps —
about 120 kbps down, on a topic layout that is already per sender and needs no change.

That is worth comparing against the alternative honestly. A WebRTC mesh has every participant
send a separate copy to every other, so five people is four upstreams each: the same call costs
four times the upload on the phone with the worst connection, which is usually the one holding
it. Avoiding that normally means running an SFU, which is a server. The broker already is one,
and it is a server these groups already have.

#### What changes on the wire: almost nothing

The five messages from phase 8 carry a group call unchanged. Only two things shift, and one of
them is a change of meaning rather than of bytes:

- **`offer` may omit its target.** Present means "ring this one member", exactly as now. Absent
  means "ring the group". Nothing else about the message changes, and an older build declines to
  decode an offer with no target — so it simply does not ring for a group call rather than
  misinterpreting one, which is the right way for this to degrade.
- **`end` means "I have left", not "the call is over".** For two people those are the same
  sentence, which is why phase 8 could use the shorter one. For a room they are not: one person
  leaving is not the room closing. No bytes change; the machine's reading of them does.

`accept` likewise becomes "I am joining" rather than "I am picking up" — again the same thing
when there are two of you.

#### How a late joiner learns who is already there

Nothing is retained on `call`, deliberately (see [Topics.call]), so there is no roster to read on
arrival. The room is reconstructed from the traffic instead: **a participant who is already in
the call answers a new `accept` with its own.** A phone joining an established call hears one
`accept` back from each person present and builds the list from those.

Two things keep that from becoming a storm. It is only sent in reply to somebody *new* — an
`accept` from a participant already known produces nothing — and only by phones that are
themselves connected. So a join costs one message out and N back, once, with N the size of a
family. The alternative, a periodic roster heartbeat, spends bandwidth forever to avoid a burst
that happens when somebody joins.

#### What changes in the state machine

[CallState.Connected] holds a **set** of participants rather than one peer, and [CallState.Ended]
records why *we* left rather than what happened to a call that may still be running without us.

The rules worth stating, because they are the ones that are easy to get wrong:

- **A call with nobody else in it is over.** When the last other participant leaves, so do we.
  Sitting in an empty room waiting is not a state anyone wants to be shown.
- **Ringing still times out**, and for a group offer that means: if nobody has joined by the time
  the offer expires, the call ends unanswered. If somebody has, the offer expiring is irrelevant
  — the call is up, and late joiners are welcome until it ends.
- **Only the invited may join.** For a targeted offer that is one member; for a group offer it is
  any member of the group. Since every member can decrypt the signalling either way, this is a
  rule the honest clients keep rather than one the crypto enforces — the same limitation
  everything else in this app has, and the UI must not claim otherwise.
- **Busy is still busy.** One call at a time per phone, group or not.

#### What changes in the audio

- **A jitter buffer per speaker**, keyed by sender. One buffer cannot hold two interleaved
  streams, and the `streamId` that distinguishes a second call from a first does not
  distinguish two people talking at once — the sender does, and the topic already carries it.
- **Mixing.** Every speaker's 20ms slot is summed into one output frame. Summing 16-bit samples
  overflows the moment two people talk, so it accumulates in 32 bits and clips at the ends; that
  is audibly better than wrapping, which turns a loud moment into a burst of noise.
- **Silence is not sent.** A group call where four phones publish 24 kbps of room tone is four
  times the traffic for nothing. Speech detection is out of scope here, but a phone that is
  muted already sends silence frames and those compress to almost nothing in Opus, so the muted
  case — the common one on a call with several people — costs very little.

#### Found on the first group test: it rang, and then nothing

The group rang on every phone. Answering connected nobody, and declining did nothing either.

`Outgoing.peerId` is null for a group call — that is what "rung to nobody in particular" means —
and the check that a reply comes from someone actually in this call read `state.peerId ==
senderId`. For a group call that is `null == senderId`, so **every accept, ring and decline from
every member was dropped before it was handled**. A direct call was unaffected, because there
`peerId` is the person being rung, which is why direct calls had worked all along.

The check now allows any sender while a *group* call is ringing, since anyone in the group may
answer one. And a decline no longer ends a group call: one member saying no is not the call
failing, because the rest are still ringing — a group call ends when nobody answers, not when
somebody declines.

What let this through is worth writing down, because it is the second time in this feature. The
group tests covered the *callee* thoroughly — ringing, joining, the roster, leaving, an emptied
room — and the **caller** side of a group call had no test at all. Every one of the four
behaviours above is now tested from the caller's seat, which is where the hole was.

#### The test that should have existed from the start

Both bugs in this feature — phase 8's ringing and phase 10's group call — were in a **seam**: a
message one side published and the other side dropped. Neither side's own tests were wrong. The
codecs agreed on bytes, the machine agreed on transitions, the jitter buffer agreed on slots, and
the feature did not work.

So `CallConversationTest` (and its twin `callConversation.test.ts`) drives several machines
against each other through a relay that behaves like the broker — everything published reaches
everyone else, including the sender's own copy, exactly as a group topic does. The tests press
buttons and assert where people ended up: ibu is in a call with ayah, adik joined and can see
both of them, the room survived ibu leaving. Nothing inspects a transition.

Nine scenarios, the same nine in both implementations, which is what keeps the two honest about
*behaviour* rather than only about bytes. Verified by putting the phase 10 bug back: four of
them fail, with `expected:<[ibu]> but was:<null>`.

#### The UI

Calling a group is a second entry point, beside the per-member Call button that already exists:
one on the group screen for the whole group, one per member for a direct call. The call screen
grows a participant list, since "who is actually in this call" is the question a group call asks
and a single name cannot answer.

#### Why video waits

Video is roughly twenty-five times the bitrate of voice, and the harder problem is that MQTT
runs over TCP. TCP head-of-line blocking is precisely what real-time video cannot tolerate: one
lost segment stalls every frame queued behind it until it is retransmitted, which is why WebRTC
uses UDP and not TCP. Voice at 24 kbps mostly survives that; video at 600 kbps generally will
not, outside a good local network. Keyframes make it worse in bursts, and on a shared public
broker it would be plainly abusive.

None of that makes video impossible here — on a self-hosted broker on a site's own network it is
reasonable, which is the deployment this app is aimed at anyway. But it is a decision that
deserves real numbers from a real call, and there has not been one yet. So it waits for phases 8
and 9 to be verified on hardware, and the per-sender topic layout generalises to a video topic
whenever that happens.

### Phase 11 — Buzz (MVP6)

A call became a buzz: make that phone ring, and nothing else.

#### Why

Voice works — two phones over a broker, confirmed — and it costs a steady ~36 kbps each way for
as long as people talk, through infrastructure somebody pays for and may be sharing. Set against
what a call was actually being used for, that is a poor trade. "Where did I leave my phone" and
"pick up, it is urgent" do not need a voice channel; they need a noise at the other end.

So the UI offers a buzz and nothing else. **The voice path is kept, not deleted**: it is written,
tested and working, `Call.Mode.AUDIO` still carries it, and it becomes reasonable again the
moment the broker is one you own — which is the deployment `README.md` is aimed at anyway.
Nothing in the app sends that mode today.

#### What it costs to send

An offer, a ring, and a stop. Three messages of a few hundred bytes for the whole thing, against
roughly 270 KB a minute in each direction for a voice call.

#### Three states, and only three

Calling while the request is going out, Ringing once a phone has it, Stopped once anybody stops
it. A buzz has no busy, no declined and no missed: **every way it ends is somebody stopping it**,
and inventing distinctions between those would be reporting on the mechanism rather than on what
happened. Either end can stop it — whoever reaches a phone first — which is why there is one
button at each end and no Answer.

The machine refuses `Accept` for a buzz outright, rather than leaving it to the UI not to offer
one. A buzz that reached `Connected` would be a call whose own screen has no way out of it.

#### It rings through silent, deliberately

On Android a buzz plays on the **alarm** stream, which is the one the platform leaves audible
when the ringer is off. A find-my-phone that respects the silent switch cannot find a phone on
silent, and every find-my-device feature makes the same choice for the same reason.

That is a real thing to hand someone, so the UI says it before anybody presses the button rather
than after: *"Rings their phone even if it is on silent."* A family member who can override your
silent switch should not be a surprise.

#### `buzz` is a mode, not a new message

`Call.Mode` gained a second value and the wire is otherwise untouched — which is exactly what
that field was built for. An older build refuses to decode a mode it does not know, so a phone
that has not updated stays silent rather than ringing for something it cannot represent. A buzz
also rings for 90 seconds rather than 45: finding a phone takes longer than waiting for a person
to pick up, and nobody is being kept waiting while it happens.

## Settled

- **Broker.** The user sets their own; the config screen ships a prefilled suggestion pointing
  at a public open-source broker (`test.mosquitto.org`, TLS on 8886) so a first run works
  before anyone stands up their own. The screen says in plain words that a public broker sees
  topic names and traffic timing — never message content — and that self-hosting Mosquitto or
  EMQX is the private option.
- **Location history is published to all members.** Everyone in the group holds everyone's
  history, so any phone can draw the group's past without a server. Consequence to keep in
  mind: retention is enforced per-device, so a member who set "forever" keeps your track after
  you pruned yours. New joiners are *not* backfilled — they see only what is published after
  they join, because the broker retains just the latest fix per person.
